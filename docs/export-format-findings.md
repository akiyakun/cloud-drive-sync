# Google Drive 書き出し形式の検証結果

Google Drive から取得したファイルを、AI（Claude Code）がどの形式なら正しく読めるかを確かめた記録。

- 検証日: 2026-10-11（2026-10-12 にテストデータでの検証と、変換方式の見直しを追記）
- 読み手: Claude Code。ファイル読み取り機能は、テキスト・画像・PDF に対応している。XLSX には対応していない
- 検証データ（中身は非公開）
  - テスト用フォルダ: Google ドキュメント 10、Google スプレッドシート 22、サブフォルダ 8
  - 個別ファイル: 画像を多く使った企画書スプレッドシート 1 件（16 シート、画像 61 か所・41 種類、約 6MB）

## まとめ

| Drive 上の種類 | 形式 | 文章・表 | 画像・図 | 位置関係 | 使い道 |
|---|---|---|---|---|---|
| Google ドキュメント | Markdown（Google の書き出し） | ◎ | ✕（図形描画・一部の画像・色が消える） | ○ | チェックリストの補助にだけ使う |
| Google ドキュメント | Markdown（HTML 書き出しから生成） | ◎ | ◎（図形描画も画像で残る） | ○ | **AI が普段読む本体** |
| Google ドキュメント | PDF | △（表の構造が崩れる） | ◎ | ○ | Markdown を作れなかったときの保険 |
| Google スプレッドシート | XLSX | ✕（直接読めない） | ✕（直接読めない） | ◎（データとしては保持） | 変換元・原本の保管 |
| Google スプレッドシート | Markdown（XLSX から生成） | ◎ | ○（画像は別ファイル、図形描画・グラフは文章で記録） | ○（セル番地付き） | **AI が普段読む本体** |
| Google スプレッドシート | PDF | △〜✕（下記参照） | ◎ | △ | Markdown を作れなかったときの保険 |

**方針: AI は Markdown と、そこから参照される画像ファイルを読む。PDF は Markdown を作れなかったときの保険としてだけ作る**（→「PDF の扱いについての方針」）。PDF の文字データは、検索や引用には使わない（文字化けや構造の崩れがあるため）。

## Google ドキュメント

### Markdown（`text/markdown` で書き出し）

> 2026-10-12: 図形描画などが消えることが分かったため、本体は「HTML 書き出しから生成した Markdown」に切り替えた（→「HTML 書き出しから生成した Markdown」）。以下は最初に検証したときの記録。

- 見出し・表・箇条書き・リンクは、きれいに変換される。
- ドキュメントの**タブが複数あっても、すべてのタブが出力される**（タブ名が見出しになる）。
- `\_` や `\>` などの記号の前に `\` が多く付くが、読むのには困らない。
- **画像の問題**: 画像は、画像データを文字列にした形（base64）で、ファイル末尾にそのまま埋め込まれる。
  ```text
  本文中:   ![][image1]
  末尾:     [image1]: <data:image/png;base64,iVBORw0KGgo...（非常に長い）>
  ```
  - 画像入りのファイルは、**中身の 98〜99% が画像の文字列**だった（例: 全体 470KB のうち、文章は 8KB）。
  - AI はこの文字列を画像として見られない。読み込むと、意味のない文字を大量に読むことになる。
  - 当初は `sync.py` で画像を `<名前>.images/` フォルダに取り出して対応していた（Markdown は元の 1/30〜1/250 の大きさになった）。HTML 書き出しへの切り替えで、この処理は不要になった。

### HTML 書き出しから生成した Markdown（`markitdown_ext/google_docs.py`）

HTML 書き出し（`application/zip`。`index.html` と `images/`）を読み、自分で Markdown にする。

- 見出し・段落・太字・斜体・取り消し線・リンク・箇条書き（番号付き・階層付き）・脚注・表に対応。
- **図形描画**は HTML では PNG 画像になっているので、ほかの画像と一緒に `<名前>.images/` に取り出す。
- 文字の色は `〔文字色A:その文字〕`、ハイライトは `〔色A:その文字〕`、下線は `<u>…</u>`。黒・灰・白の文字とリンクの青には印を付けない。
- 表のセルの背景色は `〔色A〕`、結合は `〔結合 横2×縦1〕`。結合で隠れたセルは空にする。表の 1 行目は見出し行として扱う。
- リンクは Google の中継（`https://www.google.com/url?q=…`）を外して、本来のリンク先にする。
- **チェックリスト**は HTML では普通の箇条書きになるので、Google の Markdown 書き出しも取得し、同じ文字の項目に `- [ ]` / `- [x]` を付ける（取得に失敗しても変換は続ける）。
- タブの名前は `# タブ名` の見出しになる（Google の Markdown 書き出しと同じ）。
- 脚注の前の区切り線と改ページは出さない。
- コメント（`cmnt`）の書き出しにも対応したが、文字に付けたコメントを含む資料でまだ確認していない。

実データ（ドキュメント 10 件）で、古い方式（Google の Markdown 書き出し）と比べた結果:

- **文章の抜けはなかった。**違いは、空の見出し `# ` が出なくなったことと、見出しの後ろの `{#…}`（ページ内リンクの飛び先の目印）が付かなくなったことだけ。ページ内リンクは、リンクではなく文字として出る。
- **古い方式で黙って消えていた画像が 2 件見つかった**（どちらも画面のスクリーンショット）。Google の Markdown 書き出しは、本文に貼った画像の一部（文字の回り込みなどの配置にした画像とみられる）を出力しない。
- 色の印は、見出しの色付き文字にも付く（例: `# 〔文字色A:…〕`）。

### PDF

- 画像（スクリーンショットなど）の中身を、AI が目で見て理解できた。
- 見出しごとに改ページされる設定の資料では、**ほぼ白紙のページが多く出る**。
- 文字として読み取ると、**表の罫線構造が失われる**（セルの中身が並ぶだけになる）。

## Google スプレッドシート

### XLSX

- 次の情報がすべて保持される: シート、セルの値、画像（`xl/media/`）、**画像がどのセルの辺りにあるか**（`xl/drawings/` の位置情報）。
- 書き出したファイルを Excel や Numbers で開くと、貼られた画像も残っていた。
- **Claude Code はそのままでは読めない。**変換処理が必要になる（→ 下の「XLSX から生成した Markdown」）。
- 図形・テキストボックス・グラフを含むファイルは、今回のデータに無かったので未検証。
- Google の「コメント」は、Excel の**スレッド形式コメント**として入る。先頭に Excel の英語の定型文（`[Threaded comment] Your version of Excel ...`）が付く。「メモ」は普通のコメントとして入る。

### XLSX から生成した Markdown（`markitdown_ext/xlsx.py`）

XLSX を openpyxl で読み、シートごとに次の内容を書き出す。

- **セル番地付きの表**（列名 A, B, C… と行番号付き）。値のある範囲だけを出す。
- **画像**: `<名前>.images/` に取り出し、**どのセルの辺りに貼られているか**（例: `E27`）を位置順に一覧にする。同じ画像が何か所に貼られていても、ファイルは1つだけ保存する。
- **セルのメモ・コメント**: スレッド形式コメントの英語の定型文は取り除く。
- **セルの背景色**: セルの文字の後ろに `〔色A〕` のような記号を付け、シートの先頭に対応表（`〔色A〕 #F4CCCC（薄い赤）: 16 セル`）を出す。
  - 同じ記号は、ファイル内のどのシートでも同じ色。
  - 白は「色なし」として扱う。値のある範囲の半分以上を占める色は「シートの背景色」として 1 回だけ書き、セルごとには付けない（全体を塗ったシートで記号だらけになるのを防ぐ）。
  - 色名（薄い赤、濃い緑など）は、色相と明るさからおおまかに付けている。
- **取り消し線**: `~~文字~~` で残す（「やめた案」を表すことが多いため）。

検証結果（23 ファイル、すべて変換に成功）:

- **PDF で起きていた日本語の文字化けは起きない**（PDF ではなく、セルの値そのものを読むため）。
- **セルで作った画面遷移図も、セル番地のおかげで位置関係（どこからどこへの矢印か）を追える。**
- **PDF には出ていなかったコメントも読める。**PDF に出るのは「メモ」だけで、「コメント」は出ていなかった。
- 画像の多い企画書（画像 61 か所・41 種類）でも、すべての画像を取り出し、位置を記録できた。
- 1 ファイルの変換時間は 0.1 秒程度。
- 背景色はすべて単色の塗り（solid）で、色は全体で 25 種類だった。
- **凡例付きの色分けも、凡例のセルと同じ記号が付くので、色の意味を Markdown だけで読み取れた。**（例: 遷移図の「まだ仕様ができていない」色が付いた画面を特定できた。PDF の見た目とも一致した）
- 数式は、セルに保存されている計算結果の値で出す。
- **文字の色**: 背景色と同じ記号の仕組みで `〔文字色A〕` を付ける（アルファベットは背景色と共通で、同じ色なら同じ記号）。
  - 黒・灰・白の文字（普通の文字や、濃い背景の上の白文字）と、リンクの青には付けない。
  - 文字色が「テーマ色」で指定されたセルは、検証データではすべて普通の黒文字だったので扱っていない。
  - 色付きの文字は検証データ全体で 2 セルだけだった。どちらも「目立たせたい意見・注記」だった。
  - セルの中の**一部の文字だけ**に付けた色は、まだ扱っていない。
- まだ書き出していないもの: 太字、列幅、画像の大きさ・重なり方。（セルの結合とセル内の一部だけの色は 2026-10-12 に対応。「テストデータでの検証」を参照）

### PDF

- 縦に長いシートは、複数ページに分かれて正しく続く。
- 空のシートも白紙ページとして出力される。
- **横に広いシートは、1ページの幅に収めるため縮小され、ほぼ読めない。**文字として読み取ると、行と列が混ざる。
- **日本語の文字化け**（一部のファイルで発生）: 見た目は正常なのに、文字として読み取ると、一部のひらがなが別の文字（CJK統合漢字拡張A）になる。
  | 本来の文字 | 読み取った文字 |
  |---|---|
  | の | 䛾 (U+46FE) |
  | は | 䛿 (U+46FF) |
  | ば | 䜀 (U+4700) |

  フォントによる問題とみられる。同じ書き出し方でも、文字化けしないファイルもあった。
- **セルで作った図**（セルの配置・色・矢印の文字で描いた画面遷移図など）:
  - 見た目は残るが、縮小されて細部が読みにくい。
  - 文字として読み取ると、位置関係（どこからどこへの矢印か）が失われる。
  - **セルの色に意味があっても**（凡例付きの色分けなど）、文字にすると色の情報は消える。
- セルのメモ（コメント）は、PDF の最後のページにまとめて出力される（本文側には `[1]` のような番号だけが入る）。

## 共通の制約・注意

- **書き出しの大きさの上限は 10MB**（Google Drive API の仕様）。画像の多いスプレッドシートは、XLSX も PDF も約 6MB あった。書き出しに失敗したときは `sync.py` が「失敗」として記録し、ほかのファイルの処理は続ける。代わりの手段は未決定。
- Claude Code で PDF を**ページを指定して**読むには、`pdftoppm`（poppler）が必要だった。ページを指定しなければ、未インストールでも全体を読めた。
- **出力データそのものが秘密情報になりうる**。人名、社内資料や Discord へのリンク、未発表の企画内容などが含まれる。
  - `output/` は `.gitignore` で除外している。
  - NAS に置くときは、共有フォルダを誰が見られるかを絞る。

## テストデータでの検証（2026-10-12）

`dev/make_test_data.py` で作ったダミーの資料に、API では作れない「図形描画」と「シート上に浮かせた画像」を手で足して検証した。

### Google ドキュメント: Google の Markdown 書き出し と HTML 書き出し（`application/zip`）の比較

| 項目 | Markdown 書き出し | HTML 書き出し |
|---|---|---|
| 見出し・太字・斜体・取り消し線・リンク | ✅ | ✅（リンクは `google.com/url?q=` を経由する形になる） |
| 文字の色・ハイライト・下線 | ❌ 消える | ✅ `style="color:#ff0000"` などで残る |
| 表のセルの背景色 | ❌ 消える | ✅ `<td style="background-color:…">` |
| 表のセルの結合 | ❌ 空のセルになり、結合かどうか分からない | ✅ `colspan` で残る |
| **図形描画** | ❌ **完全に消える**（跡も残らない） | ✅ **PNG 画像として出る**（矢印の向きや文字も見える） |
| チェックリスト | ✅ `- [ ]` | ❌ 普通の箇条書き（●）になる |
| 脚注 | ✅ | ✅ |
| コメント | ❌ | ❌（Drive API の comments.list なら取得できる） |
| 複数のタブ | ✅（実データで確認済み） | 未確認 |

DOCX 書き出しにも、図形描画は画像として入っていた（`word/media/image1.png`）。

### Google スプレッドシート: XLSX と、そこから作った Markdown

| 項目 | XLSX に入っているか | 検証時の Markdown | 対応後（2026-10-12） |
|---|---|---|---|
| 背景色・文字色・取り消し線 | ✅ | ✅ | ✅ |
| 結合したセルの値 | ✅ | ✅（値のみ。結合している範囲は出ていない） | ✅ `〔結合 A4:C4〕` |
| セル内の一部だけの文字色 | ✅（文字ごとの書式 `<r>`） | ❌ | ✅ `一部だけ〔文字色C:赤い〕文字` |
| チェックボックス・プルダウン | ✅（値と入力規則） | △（値だけ。`True` / `選択肢B`） | ✅ 値は `TRUE`、プルダウンは「入力規則」の節に選択肢 |
| 数式 | ✅（数式と計算結果） | △（計算結果だけ） | ✅ 表は計算結果、「数式」の節に数式 |
| `HYPERLINK` 関数のリンク | ✅（数式の中に URL） | ❌（表示文字だけで URL が消える） | ✅ `[example.com](<https://example.com/>)` |
| `IMAGE` 関数の画像 | ❌（値が `#REF!` になる。数式の中に URL は残る） | ❌ | △ 画像は取れないが、URL を `![IMAGE 関数の画像](<URL>)` で残す |
| 条件付き書式 | ✅（ルールとして入る。色はセルの書式ではない） | ❌ | ✅ 「条件付き書式」の節に `B14:C14: セルの値が 50 以上 → 背景 #B7E1CD（薄い緑）` |
| **グラフ** | ✅（`xl/charts/` に種類・タイトル・データ範囲） | ❌ | ✅ 「グラフ」の節に種類・タイトル・系列のデータ範囲 |
| **図形描画** | ✅ **画像ではなく図形として入る**（四角・文字「開始」「終了」・矢印の位置と向き） | ❌ | ✅ 「図形描画」の節に `図形1「開始」 → 図形2「終了」` |
| シート上に浮かせた画像 | ✅ | ✅（位置付き） | ✅ |
| メモ・コメント・非表示シート | ✅ | ✅ | ✅ |
| 整数の値 | ✅ | △（`10.0` のように小数点付きで出る） | ✅ `10` |

検証時点では PDF を保険だけにしていたため、❌ の情報は出力のどこにも残っていなかった。ドキュメントは HTML 書き出しへの切り替えで、スプレッドシートは `markitdown_ext/xlsx.py` / `markitdown_ext/xlsx_drawings.py` の追加対応で解消した。

図形描画の文章化について:

- 図形の種類（四角形・楕円・ひし形・フローチャートの記号など）、中の文字、塗りの色を書き出す。番号は上から下、左から右の順。
- 矢印（線）は、両端がどの図形に一番近いかでつながりを判定する。XLSX につながり先の情報があればそちらを使う。矢印の向きは線の先端の形（`headEnd` / `tailEnd`）から判定する。
- グループの中の図形は、グループの座標の変換を考えて位置を比べる。
- 検証できたのは「四角 2 つと矢印 1 本」の単純な図だけ。曲がった線や、たくさんの図形が重なった図はまだ確認していない。

## MarkItDown との比較と採用（2026-10-12）

[MarkItDown](https://github.com/microsoft/markitdown)（Microsoft のオープンソース。いろいろな形式を AI 向けの Markdown にする）を、変換の土台として採用した。

### 標準の変換で試した結果（MarkItDown 0.1.8、テストデータ）

Google ドキュメントを DOCX で書き出して変換した場合:

| 項目 | MarkItDown 標準 | 自前の変換（`markitdown_ext`） |
|---|---|---|
| 太字・斜体・下線・取り消し線・リンク・脚注 | ✅ | ✅ |
| 文字の色・ハイライト | ❌ | ✅ |
| 表のセルの色・結合 | ❌（結合は空のセルになるだけ） | ✅ |
| 図形描画・画像 | ❌ `![](data:image/png;base64...)` と中身が省かれる | ✅ 画像ファイルとして保存 |
| チェックリスト | ❌ 普通の箇条書き | ✅ `- [ ]` |
| タブ名 | △ 普通の段落 | ✅ `# タブ名` |

XLSX を変換した場合:

- 表計算ライブラリ（pandas）で読むため、1 行目が表の見出しになり、空のセルは `NaN`、見出しのない列は `Unnamed: 1` になる。
- セル番地・色・結合・メモ／コメント・数式・リンク先・画像・図形描画・グラフ・条件付き書式・プルダウン・非表示かどうかは、すべて消える。

Vision AI（画像の説明文を作る機能）は、ソースコードを確認したところ、画像ファイルそのものと PowerPoint（.pptx）の画像にだけ使われる。DOCX・XLSX の中の画像には使われない（ただし、画像の扱いを差し替える口 `_image_to_html` は用意されている）。

### 方針

- **MarkItDown を共通の入り口にし、出力の基本の形（見出し・GitHub 形式の表・`![](画像)`）をそろえる。**そのうえで、色の印・セル番地・「図形描画」「グラフ」などの節といった自前の拡張は残す。
- 標準の変換で情報が消える形式は、**自前の変換部品をプラグインとして差し込む**（`markitdown_ext/`）。元々の .xlsx / .docx 資料も、標準の変換では情報が欠けると予想されるので、同じように拡張していく。
- 自前の部品で対応していない形式（.pptx・PDF・CSV など）は、MarkItDown 標準の変換を使う予定。
- [Docling](https://github.com/docling-project/docling) は、MarkItDown で対応しきれない場合（スキャンした PDF など）の補助の候補。機械学習のモデルを使い、入れるものが大きいので、必要になってから検討する（今回は試していない）。

### 仕組み（`markitdown_ext/`）

| ファイル | 役割 |
|---|---|
| `__init__.py` | プラグインの入り口。`register_converters()`（MarkItDown のプラグインの決まり）と、登録済みの MarkItDown を作る `create_markitdown()` |
| `xlsx.py` | `XlsxConverter`: .xlsx の変換部品（Google の書き出しに限らず使える） |
| `xlsx_drawings.py` | シート上の画像・図形描画・グラフの読み取り |
| `google_docs.py` | `GoogleDocsZipConverter`: Google ドキュメントの HTML 書き出し（zip）の変換部品 |
| `colors.py` | 色の記号・色名の共通処理 |
| `result.py` | `ConversionResult`: MarkItDown の結果に、取り出した画像の一覧（`images`）を足したもの |

- 自前の部品は MarkItDown 標準の部品より先に試される（同じ優先度なら、後から登録した部品が先）。
- **自前の部品が失敗すると、MarkItDown は標準の変換を試す。**標準の変換で成功すると情報が欠けた Markdown になるので、`sync.py` では自前の部品の結果（`ConversionResult`）でなければ失敗として扱い、保険の PDF に回す。実際に、壊れたファイルを渡すと標準の文字変換が「成功」してしまうことを確認した。
- MarkItDown は結果の各行の末尾の空白を削るので、段落内の改行は「行末の空白 2 つ」ではなく `<br>` で表す。
- 作り変えの前後で、スプレッドシート 24 ファイルとテスト用ドキュメントの出力が 1 文字も変わらないことを確認した。
- 種類の指定がない zip ファイルでも、中身（`index.html` と `images/` だけで、`doc-content` を含む）から Google ドキュメントの書き出しかどうかを見分ける。

## PDF の扱いについての方針

- 「この資料には PDF が必要か」を資料ごとに設定する方式は採らない。**設定する人がすべての資料の中身を把握している必要があり、運用が難しいため。**
- 代わりに、**Markdown（と取り出した画像）だけで資料の情報が足りる状態**を目指す。
- **決定（2026-10-12）: PDF は保険とし、Markdown を作れなかったときだけ作る。**ドキュメントとスプレッドシートが対象。
  - 例: Markdown の書き出しが 10MB の上限を超えた、XLSX の変換中に想定外のエラーが出た。
  - 実行結果に「PDF で代替」として件数と理由を表示する。
  - スライドは Markdown 化が未実装なので、今まで通り PPTX と PDF を作る。
- PDF をやめたことで失われる情報（2026-10-12 時点）:
  - ドキュメント: 図形描画や文字の装飾などが Markdown に出るかは未検証（→ テスト用の資料で確認予定）。
  - スプレッドシート: セルの結合・列幅などの見た目の配置、画像の大きさ・重なり方、セル内の一部だけの装飾。
- 参考: 検証データでは、出力全体の約 4 割（12.2MB）が PDF だった。
- 注意: 以前に作った PDF は、自動では消さない（削除の扱いは未決定のため）。不要なら `output/` を手で消してから同期し直す。
